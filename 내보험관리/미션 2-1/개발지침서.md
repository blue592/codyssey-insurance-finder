# 내보험 관리 대시보드 — 신규 개발지침서 v1.0

기존 기획서 원본을 수정하지 않은 별도 문서다. 이후 병합할 때 사용한다. 현재 산출물은 설계이며 HTML 구현·기능 이식·시각 검증 완료를 뜻하지 않는다. 대화에서 확인된 요구사항을 정리했으며 다른 대화의 전체 원문을 복원한 기록은 아니다.


## 01. 범위와 결정 우선순위

- 대상: 본인 1명이 PC·모바일에서 쓰는 보험 관리 대시보드. 공개 저장소 제출과 개인 사용은 양립하며 공개 자료에는 가상 데이터만 넣는다.
- 기존 기획서·기존 숨은보험금찾기 HTML·개인 백업 원본은 그대로 보관한다. 이번 문서는 새 기획서의 상세 구현 기준이다.
- 적용 순서: 최신 사용자 요청 → 이 문서의 최종 요구사항 → 화면별 기준 시안 → 과거 기획서. 이미지의 오래된 이름·예시값은 최신 요청으로 교체한다.
- 기존 예상보험금 계산기와 이번 가입정보 관리 화면은 단계적으로 합친다. 가입금액 합계는 예상 지급보험금이 아니다.
- 신규 기획서에는 요청된 9개 항목만 둔다. 완료 기준은 정확히 8개, 한계·비목표는 3개, 검증 방법은 1개다.

| 대화에서 정한 내용 | 최종 적용 |
| --- | --- |
| 회사별 보기 | ‘계약별로 구분’으로 변경, 계약마다 한 행 |
| 자료 관리 | ‘내보험 추가하기’로 변경, 기존 등록 기능 재사용 |
| PC 첫 화면 | 파스텔 대시보드 |
| 모바일 | 아이콘+한글 라벨, PC와 같은 정보·기능 |
| 보장별 | 질병·상해·운전·기타 4개 대분류 |
| 신체별 | 대시보드 내 탐색 유지 |
| 계약 상세 | 해당 상품에 가입된 모든 보장 표시 |
| 디자인 | 모든 기존 시안 보존, 최신 변경사항만 명시적으로 반영 |
| 문서 | 원본 유지, 신규 기획서와 개발지침서 분리 |

## 02. 실행 구조와 데이터 보존

단일 HTML에 CSS·JavaScript·아이콘을 포함한다. 서버·로그인·API·CDN 없이 기본 관리가 가능해야 한다. 외부 변환 서비스 안내 링크는 별도 온라인 작업이며 오프라인 자동 변환으로 표현하지 않는다.

IndexedDB를 사용하며 기존 앱과 이름 공간을 분리한다. 신규 DB 이름 예시는 `hidden-insurance-manager-v1`이며 기존 실제 이름을 확인한 뒤 확정한다. 앱 버전·DB 버전·백업 버전·문서 버전을 따로 기록한다.

원본 백업의 알 수 없는 필드·타입·ID·계약/담보/문서 관계·규칙·이력까지 보존한다. 원본 바이트 사본과 읽기용 어댑터를 두고, 화면용 정규화 결과 및 사용자 수정은 분리한다. 분류 실패를 이유로 원본 행을 삭제하지 않는다. 실제 스키마를 확인하기 전 새 형식으로 덮어쓰지 않는다.

| 엔터티 | 필요한 값 |
| --- | --- |
| 계약 | 고유 ID, 보험회사, 상품명, 계약구분, 실제 월 보험료, 계약기간, 납입기간, 원문 연결 |
| 담보 | 계약 ID, 담보 ID, 원래 특약명, 설명, 가입금액, 원래 단위, 보장기간, 조건·근거 |
| 분류 | 대분류, 그룹, 세부 분류, 급부 종류, 신체 부위, 공통 여부, 사용자 수정 여부 |
| 문서 | 원본 ID·파일명·유형·해시, 계약 연결, 원문 위치, 변환본 연결 |
| 작업 상태 | 파일별 진행률, 완료/실패 구간, 재개 위치, 검토 상태 |

숫자 미확인은 0으로 바꾸지 않고 ‘확인 필요’로 표시한다. 일반 백업에도 계약과 담보 데이터는 모두 있어야 하며 ‘원본 제외’는 연결된 원본 파일의 바이트 제외를 의미한다.

## 03. 시안 재현 규칙 — 필수 준수

**첨부 시안은 분위기 참고가 아니라 화면 구현의 기준이다. 임의로 새 디자인을 만들지 않는다.** 11장의 이미지 원본을 먼저 열고, 각 화면의 영역·배치·비율·색상·모서리·그림자·아이콘을 추출한 뒤 구현한다.

| 요소 | 재현 기준 |
| --- | --- |
| 전체 구성 | 선택한 화면 시안의 사이드바·헤더·본문·요약 카드 위치와 상대 비율 유지 |
| 카드 | 카드 수·순서·정렬·여백·모서리·그림자를 기준 이미지에 맞춤 |
| 색상 | 민트·분홍·라벤더·연노랑·크림의 실제 이미지 색을 샘플링해 토큰으로 기록 |
| 글자 | 한글 가독성, 제목/본문/금액의 상대 크기와 굵기 재현. 이미지의 오탈자는 확정 문구로 교정 |
| 아이콘 | 귀여운 표정·둥근 선의 장기/세포 아이콘. 이모지만으로 대체하지 말고 일관된 자체 SVG 제작 |
| 회사 로고 | 확인된 실제 로고 자산 사용. 없는 경우 회사명 텍스트. 가상 로고를 실제 회사 로고로 표현하지 않음 |
| 반응형 | PC 시안을 그대로 축소하지 않고 모바일 시안의 카드·간격·탐색 구조 적용 |
| 상호작용 | 활성 상태·펼침·닫힘·뒤로가기·표 스크롤까지 같은 디자인 체계 적용 |

시안에 없는 상세 동작은 기존 컴포넌트를 재사용한다. 새 화면을 마음대로 꾸미지 않고 해당 화면이 ‘시안 미제공·같은 디자인 체계로 확장’임을 개발 기록에 적는다. 내보험 추가하기의 최신 독립 시안은 현재 묶음에 없으므로 완전한 원본 픽셀 일치 대상으로 주장할 수 없다.

구현 전 `디자인 토큰 표`를 작성한다: 배경색/카드색/강조색/텍스트색, 글꼴, 제목·본문·금액 크기, 사이드바 폭, 본문 폭, 카드 간격, 패딩, 반경, 그림자, 아이콘 크기. 아래 수치는 초기 구현 가이드이며 시안 실측값이 우선한다: 8px 간격 체계, 카드 반경 20~28px, 터치 영역 44px 이상, 본문 대비 4.5:1 이상. 접근성 조정은 변경 이유를 기록한다.

**시각 검수 절차:** 기준 이미지에서 앱 영역을 분리해 기준 화면 크기를 기록 → 동일 크기 브라우저 캡처 → 원본과 좌우 비교 및 반투명 겹침 → 위치·크기·색상·줄바꿈 차이 기록 → 수정 후 재캡처. 기본 검수 폭은 PC 1440/1280, 모바일 390/375px이며 실제 시안 앱 영역 비율도 별도로 맞춘다. 모바일은 가로 넘침·하단 메뉴 가림을 검사한다. 단, 계약 표 안의 의도된 가로 스크롤은 허용한다.

같은 뷰포트에서 주요 카드·열·버튼의 위치와 크기는 기준 대비 약 4px 이내를 목표로 하고, 색 토큰은 샘플링 값과 일치시킨다. 글꼴 렌더링 차이·동적 데이터 길이·생성 이미지 특유의 불일치는 별도 기록한다. 이 수치는 제안된 검수 기준이지 현재 측정된 결과가 아니다. 단순히 ‘파스텔톤’만 비슷하면 완료로 판정하지 않는다. 정적인 생성 이미지가 기능·폰트·모바일 줄바꿈까지 100% 동일함을 보장하지는 않으므로 최종 화면 캡처로 확인한다.

## 04. 메뉴·대시보드·신체별 보기

최종 메뉴는 `대시보드 / 계약별로 구분 / 보장별 분류 / 내보험 추가하기`다. PC는 첫 시안의 대시보드 구성을 기준으로, 모바일은 해당 모바일 구성을 기준으로 한다. 현재 메뉴는 연한 민트 활성색과 텍스트·형태로 함께 구분한다.

대시보드에는 등록 계약 수·보장 수·확인 필요 항목, 계약 요약과 보장별/신체별 진입을 제공한다. 시안의 금액은 가상 예시이며 실제 데이터에 없는 합계·건수를 고정 표시하지 않는다. 빈 데이터는 등록 안내를 보여준다. 추가 기능인 월 보험료 합계는 확인된 월납 금액만 대상으로 하고 제외 계약을 표시한다.

신체별은 뇌·심장·치아·간·폐·신장·소화기·뼈/관절·눈·피부 등으로 연결한다. 암은 세포 아이콘을 사용하며 반드시 특정 신체부위로 단정하지 않는다. 전신·공통·미분류를 둔다. 동일 담보가 여러 신체 필터에 나타나도 원본은 하나다. 신체별 탐색으로 질병 위험도나 건강 점수를 생성하지 않는다.

PC·모바일에서 같은 계약·담보 ID를 사용한다. 아이콘에는 한글 라벨을 병기하고 키보드 포커스·스크린리더 이름을 제공한다. 뒤로가기는 직전 분류와 스크롤 위치를 복원한다.

## 05. 계약별로 구분 — 표와 로고

| 보험회사명 | 보험상품명 | 보험료 | 상세보기 |
| --- | --- | --- | --- |
| [회사 로고] ○○보험 | 건강보험 | 월 50,000원 | 상세보기 |
| [회사 로고] ○○보험 | 암보험 | 월 30,000원 | 상세보기 |

위 금액은 가상 예시다. 계약 하나당 한 행이다. 회사·상품명이 같아도 계약 ID가 다르면 별도 행이다. 기본 열 이름과 순서는 그대로 유지한다. 로고는 보험회사명과 같은 셀에 두고 대체 텍스트를 넣는다.

보험료는 실제 매달 내는 금액이다. 보장 가입금액과 절대 혼용하지 않는다. 연납·분기납·납입완료·미확인은 원래 납입정보와 확인 상태를 보존하며 임의로 12등분하거나 0원으로 표시하지 않는다. 실제 월납 여부를 확인해 입력한다.

PC·모바일 모두 4열 표 구조를 유지한다. 모바일은 상품명 줄바꿈과 표 내부 가로 스크롤을 허용하고 상세보기 버튼을 누르기 쉽게 만든다. 회사별 합쳐진 행이나 회사별 총 보장액 화면으로 되돌리지 않는다.

## 06. 내보험보기 — 하나의 증권처럼

## 08. 가입금액 집계와 근거 펼치기

화면 명칭은 ‘보장별 분류’다. 합계 명칭은 ‘가입금액 합계’이며 질병 검색 결과의 ‘예상 지급보험금’과 구분한다.

| 세부 보장 | 예시 합계 | 구성 |
| --- | --- | --- |
| 고액암 진단비 | 5,000만 원 | 담보 2건 |
| 고액암 수술비 | 500만 원 | 담보 2건 |
| 일반암 진단비 | 3,000만 원 | 담보 3건 |
| 유사암 진단비 | 600만 원 | 담보 2건 |
| 암 입원일당 | 하루 10만 원 | 일당끼리 합계 |

모두 가상 예시다. 진단·수술·치료·일당을 각각 합산하고 원/일·원/회·일시금·비율을 섞지 않는다. 고액암·일반암·유사암을 더해 ‘암이면 받는 총액’으로 표시하지 않는다. 뇌혈관·뇌졸중·뇌출혈 역시 개별 표시한다. 실제 동시 지급 판단은 후속 약관 대조 기능의 영역이다.

실손·벌금·배상책임은 보장한도로 구분하고 계약별 한도를 보여준다. 실제 지출 보상액을 단순 합계로 제시하지 않는다. 지급 조건이 서로 다른 담보는 원문 조건과 각 금액을 확인할 수 있어야 한다. 기간이 끝난 계약·담보는 상태와 집계 포함 여부를 명시하고 기본 유효 보장 집계에서 구분한다. 기간 미확인은 별도 검토 대상으로 둔다.

집계 키는 대분류·그룹·세부분류·급부·단위·종/등급·지급형태다. 중복 제거 키는 출처 데이터셋+계약 ID+담보 ID로 관리한다. 질병과 상해를 함께 보장하는 담보는 공통 배지를 붙이고 전체 건수 집계에서 한 번만 센다. 서로 다른 계약의 같은 이름 담보는 삭제하지 않는다. 합치기 복원 시 출처 ID 충돌을 따로 검토한다.

합계를 누르면 `보험회사 → 상품명 → 원래 특약명 → 가입금액 → 지급 조건`을 보여주고 근거 문서·위치를 연결한다. 조건이 없는 경우 ‘확인 필요’로 둔다. 합계 구성 N건과 펼쳐진 N건이 일치해야 한다.

## 09. 내보험 추가하기 — 기존 기능 재사용

‘자료 관리’의 최종 이름은 **내보험 추가하기**다. 기존 숨은보험금찾기의 기능을 가져온다. 현재 문서 작성에서 원본 코드의 실제 구현 상태를 검증한 것은 아니므로 개발 시 먼저 소스를 확인한다.

1. 기존 HTML 버전·파일 해시와 등록/추출/저장 함수 목록을 기록한다. 구현 완료 / 설계만 있음 / 미확인을 구분한다.
2. 증권 업로드 영역과 약관 업로드 영역을 분리한다. MD 파일 선택·끌어놓기 및 여러 파일 등록을 지원한다. 모바일은 파일 선택을 제공한다.
3. PDF를 MD로 변환하는 안내·프롬프트 복사·기존 연결 링크를 유지한다. 문서 원문 순서·특약 전체·계약구분을 보존하고 이름·주소 등 마스킹을 안내한다. 스캔 PDF의 글자를 오프라인에서 자동 인식한다고 약속하지 않는다.
4. 회사·상품·월 보험료·계약기간·납입기간·계약구분과 모든 보장의 이름·내용·금액·기간을 추출 결과로 미리 보여준다.
5. 연결 후보를 보여주고 사용자가 증권과 약관, 계약 묶음을 확인한다. 파일 여러 개를 이름만으로 한 계약에 무조건 묶지 않는다.
6. 사용자가 수정·확인 후 하나의 계약으로 등록한다. 확인 필요 항목은 상태를 남긴다. 계약별 목록과 전체 보장 상세에 즉시 연결한다.
7. 파일별 진행률·초안·완료 구간·실패 구간을 저장한다. 중단 후 이어 하기와 실패 부분만 재시도를 지원하고 완료 담보가 중복 생성되지 않게 한다.
8. 같은 화면 안의 별도 ‘백업·불러오기’ 영역에서 기존 JSON을 복원한다. 기존 앱의 내보내기 형식을 먼저 검증한다.

증권 없이 지급 가능 검색을 허용하는 등 기존 산출기의 제약을 이번 관리화면에서 임의로 바꾸지 않는다. 증권·약관·보험정보의 등록 완료 조건은 후속 산출기에 연결할 때 기존 정책을 재검토한다. 이번 관리 단계의 미완성 계약은 초안/확인 필요로 표시할 수 있다.

## 10. 저장·백업·수정·복구

IndexedDB 자동 저장 결과를 성공/실패로 안내한다. 시크릿창·저장 공간 부족·브라우저 초기화에서는 데이터 유지가 제한될 수 있으므로 외부 백업을 제공한다. 브라우저·기기 간 이동은 백업 파일 복원으로 한다.

백업은 원본 제외/원본 포함으로 구분한다. 두 방식 모두 계약·담보·분류·수정값·연결 ID를 포함한다. 원본 제외에는 문서 메타정보와 파일 미포함 상태를 남긴다. 합치기/전체 교체 전 미리보기·건수·충돌을 보여준다. 전체 교체 전 복구 사본을 만든다. 암호화된 이전 백업은 실제 형식·기존 지원 코드를 확인하여 호환 처리하고, 지원하지 않는 파일을 빈 데이터로 덮어쓰지 않는다. 신규 잠금·암호화 기능을 임의로 추가하지 않는다.

직접 수정·분류 변경은 변경 이력과 원래 값을 남긴다. 업데이트 전 백업, 임시 DB 변환, 검증 후 전환 순서로 진행한다. 실패 시 기존 DB로 돌아가며 업데이트 이후 추가한 데이터도 별도 보존해 재적용한다. 누락 필드·손상 파일·중복 ID·취소·부분 실패에서도 원본을 유지한다.

코드와 가상 자료는 공개 GitHub 제출 가능하다. 실제 증권·약관의 개인정보·실제 백업·비밀번호·사용자명 포함 참고 캡처는 자동으로 공개 저장소에 올리지 않는다. 이번 문서 제작은 GitHub 커밋 요청으로 간주하지 않는다.

## 1. 기획 목적과 미션의 연결

### 1.1 유지할 최종 목표

기존 숨은보험금찾기의 최종 목표는 보유 보험의 증권과 약관을 대조하여 질병명 또는 진단코드를 검색했을 때 관련 보장과 계산 가능한 예상 보험금을 확인하는 것이다.

미션 2-1은 이미 완료했으므로 수정하지 않는다. 이번 문서는 미션 2-2 제작 단계의 구현 범위와 개발 순서를 정리하는 추가 문서다. 기존 기획서의 교체본으로 사용하지 않는다.

### 1.2 구현 순서를 나누는 이유

예상 보험금 계산에는 계약별 보장, 해당 약관, 적용 기간, 면책·감액, 지급 이력 등 여러 정보의 연결과 검증이 필요하다. 이를 한 번에 완성하려 하면 내보험 관리 기능까지 불안정해질 수 있다.

따라서 먼저 내보험 관리 기능을 독립적으로 사용할 수 있게 완성한다. 사용자가 자신의 보험과 가입 보장을 확인하고 자료를 안전하게 보관할 수 있는 상태를 이번 구현의 목표로 삼는다. 계산 기능은 검증된 관리 데이터에 연결하는 후속 단계로 둔다.

| 구분 | 이번 결정 | 기존 기획과의 관계 |
| --- | --- | --- |
| 미션 2-1 | 원본 유지, 수정하지 않음 | 전체 제품 목표의 기준 |
| 미션 2-2(1) | 내보험 관리 우선 구현 | 전체 기능의 첫 구현 단계 |
| 이후 개발 | 질병 검색·약관 대조·금액 계산 | 보존한 데이터에 연결하여 확장 |
| 기존 제작물·기록 | 덮어쓰거나 날짜·내용을 소급 수정하지 않음 | 이전 작업의 근거로 보관 |

후속 단계의 공식 미션 번호는 임의로 확정하지 않는다. 실제 제출 위치와 평가 항목은 수업의 원문 안내를 기준으로 확인한다. 이 문서가 평가 통과를 보장하는 것은 아니며, 구현 결과와 검증 근거를 명확하게 제시하는 데 목적이 있다.

| 기능 | 범위 |

필수 기능과 데이터 보존 검증을 완료하기 전에는 선택 기능을 추가하지 않는다. 키워드 검색 결과는 지급 가능 여부를 뜻하지 않는다.

### 4.3 후속 단계로 미룰 기능

- 질병명·진단코드로 관련 보장 자동 판정.
- 계약별 지급조건, 면책·감액·횟수·한도 자동 적용.
- 실손 비례보상 및 여러 계약의 금액 합산.
- 예상 보험금 계산, 계산 결과 확정 상태, 청구 가능 판단.
- PDF 암호 해제·OCR·일반 문서의 자동 의미 분석 고도화.
- 로그인·서버·클라우드 동기화·보험사 청구 전송.
- 복잡한 기록 분석, 다양한 출력 형식, 전체 기능 자동 업데이트.

기존 데이터에 이러한 기능의 필드나 과거 결과가 있으면 그대로 보존한다. 이번 화면에 표시하지 않는 것과 데이터를 삭제하는 것을 구분한다.

3. 불러오기 전 계약·보장·문서 수, 원본 포함 여부, 누락·충돌 여부를 확인한다.
4. 검증을 통과한 사본을 새 관리 데이터로 등록한다.
5. 대시보드에서 보험회사별·보장별·신체별로 탐색하고, 보험상품을 열어 보장과 문서를 확인한 뒤 필요한 값만 수정한다.
6. 자동 저장 상태를 확인하고 관리 백업을 내려받는다.

### 5.3 화면 문구와 예외 처리

| 상황 | 표시 및 처리 |
| --- | --- |
| 금액 존재 | ‘증권상 가입금액’으로 표시 |
| 금액 미확인 | ‘확인 필요’. 임의의 0원으로 표시하지 않음 |
| 보장기간 일부 미확인 | 원문 값과 미확인 상태를 함께 표시 |
| 증권 또는 약관 없음 | 등록·조회 허용, ‘문서 연결 필요’ 표시 |
| 원본이 빠진 백업 | ‘추출 텍스트만 있음’ 또는 ‘원본 없음’ 표시 |
| 저장 실패 | 미저장 상태를 유지하고 재시도·백업 경로 제공 |
| 가져오기 오류 | 이유를 표시하고 기존 자료와 활성 자료를 그대로 유지 |
| 해석할 수 없는 새 백업 버전 | 변환·저장 차단, 지원 버전 안내 |

관리 단계에서는 증권·약관·보험정보가 모두 있어야만 앱을 사용할 수 있다는 기존 계산용 제한을 적용하지 않는다. 부분 자료도 관리할 수 있게 하고, 계산 단계에서 필요한 조건은 후속 기능에서 별도로 확인한다.

### 5.4 개인용 대시보드 목표와 참고 이미지

본인 1명이 자신의 보험정보를 한눈에 확인하고 쉽게 관리하는 단일 HTML을 만든다. 계정 가입·회원 관리·다인 공유는 추가하지 않는다. 공개 GitHub는 코드·기획의 제출 공간이며 개인 보험정보를 공개하는 기능이 아니다.

첨부 이미지는 다음 시각적 방향의 참고 자료다. 화면에 나온 사람 이름, 금액, 건강 수치, 위험도, 보험 연결 서비스 기능은 실제 사용자 데이터나 신규 요구사항으로 가져오지 않는다. 참고 이미지 자체는 공개 저장소에 업로드하지 않는다.

| 참고 요소 | 적용할 방향 |
| --- | --- |
| 데스크톱 웰니스 대시보드 | 밝은 바탕, 둥근 파스텔 카드, 여유 있는 간격, 크기가 다른 카드의 정돈된 배치 |
| 표정이 있는 신체 아이콘 | 심장·뇌·치아·위·간·신장 등 알아보기 쉬운 귀여운 그림과 한글 이름 |
| 모바일 보장 요약 | 두 열 카드, 아이콘·분류명·항목 수, 탭하여 상세 목록 열기 |
| 모바일 건강 분석 화면 | 신체 분류의 탐색 방식만 참고. 질병 위험도·건강 점수는 표시하지 않음 |
| 모바일 파스텔 앱 | 연한 민트·하늘·노랑 카드, 간결한 하단 탐색, 큰 터치 영역 |

### 5.5 PC 첫 화면 배치

| 영역 | 내용 | 동작 |
| --- | --- | --- |
| 왼쪽 메뉴 | 대시보드 / 내보험 / 자료 관리 | 기본 진입은 대시보드, 선택 메뉴 명확히 표시 |
| 상단 | ‘내 보험 한눈에’, 내보험 추가, 저장 상태 | 파일 가져오기·직접 등록으로 이동 |
| 요약 카드 | 보험계약 수, 보장항목 수, 보험회사 수, 확인 필요 계약 수 | 각 수치에 해당하는 목록으로 이동 |
| 중앙 주요 영역 | 보험회사별 / 보장별 / 신체별 탭 및 카드 모음 | 같은 자료를 세 기준으로 탐색 |
| 보조 영역 | 문서 연결 필요, 분류 확인 필요, 최근 수정, 마지막 백업 | 해당 항목 또는 자료 관리로 이동 |
| 상세 영역 | 선택 분류의 회사·상품·보장명·가입금액·기간·원문 버튼 | 수정·문서 열람·분류 변경 |

첫 버전에서는 건수 중심으로 요약한다. 서로 다른 지급 단위·조건의 가입금액을 더해 ‘총 받을 보험금’으로 표시하지 않는다. 장식용 차트·진행률·가짜 수치를 넣지 않는다. 기본 집계는 현재 활성 자료 묶음의 보관하지 않은 항목이며 기준을 화면에 표시한다. 필터 선택은 해당 목록과 결과 건수에 적용하고, 전체 요약은 ‘전체’로 명시해 수치의 범위를 혼동하지 않게 한다.

### 5.6 세 가지 분류와 상세 연결

| 보기 | 기본 분류 | 카드 표시 | 선택 후 확인할 내용 |
| --- | --- | --- | --- |
| 보험회사별 | 등록된 실제 회사, 회사 미확인 | 회사명·중립적인 회사 아이콘·계약 수·보장 수 | 해당 회사의 계약별 상품과 보장 |
| 보장별 | 진단비·수술비·입원비·통원비·치료비·실손·후유장해·사망·기타·미분류 | 유형 아이콘·분류명·연결 보장 수 | 계약별 보장명·가입금액·단위·기간·원문 |
| 신체별 | 뇌·머리, 심장·혈관, 눈, 귀·코·목, 치아·구강, 폐·호흡기, 위·장, 간·담낭·췌장, 신장·비뇨기, 뼈·관절·척추, 피부, 여성·남성 생식기관, 전신/공통, 기타, 미분류 | 신체 아이콘·한글 이름·연결 보장 수 | 그 부위로 확인·분류한 보장과 증권·약관 근거 |

기본 목록은 탐색을 위한 초안이며 개인이 추가·이름 수정할 수 있다. ‘암’은 하나의 장기가 아니므로 보장별 보기의 선택 하위 분류(예: 진단비 → 암 관련)로 제공할 수 있다. 특정 부위가 명시되지 않은 일반암·일반 질병수술비를 모든 장기에 자동 배정하지 않고 전신/공통 또는 확인 필요로 둔다.

- 하나의 보장이 여러 분류에 연결될 수 있다. 원래 계약·보장 레코드를 복제하지 않는다.
- 카드 건수는 해당 분류에 연결된 고유 보장 ID 수다. 전체 보장 수는 자료 묶음 ID와 보장 ID 조합으로 중복 제거한다. 여러 카드의 건수를 합한 값은 전체 건수와 다를 수 있다.
- 회사별 보기에서도 같은 상품명의 다른 계약을 구분한다. 회사 별칭 정리는 화면용 매핑으로 처리하고 원문 회사명은 보존한다.
- 분류는 사용자가 직접 확인·수정한다. 키워드 기반 자동 후보는 선택적 보조 기능으로 두며 확인 전 확정 분류와 구분한다.
- 분류가 없으면 ‘미분류’로 노출한다. ‘등록된 보장 없음’과 ‘해당 보장이 보험에 없음’을 같은 뜻으로 사용하지 않는다.
- 분류 선택 → 보장 목록 → 계약 상세 → 증권·약관 원문 순서로 이동한다. 뒤로 돌아오면 선택한 보기·분류·스크롤 위치를 유지한다.
- 분류 변경은 보기용 연결을 바꾸는 작업이다. 약관의 보장 범위·지급조건이나 실제 지급 가능 여부를 바꾸지 않는다.

### 5.7 모바일 아이콘 화면

PC와 같은 첫 화면을 모바일에 맞게 재배치한다. 상단에 제목·추가 버튼, 요약 카드, 세 가지 보기 탭, 아이콘 카드 모음, 확인 필요 목록 순서로 배치한다. 기본은 두 열 카드이며 매우 좁은 화면이나 글자 확대 시 한 열로 전환한다. PC의 작은 표를 그대로 축소하지 않고 상세 내용은 세로 카드로 읽게 한다.

하단 메뉴는 ‘홈 / 내보험 / 자료 관리’의 아이콘과 한글 라벨을 함께 쓴다. 신체 아이콘에도 이름·건수를 표시하고 색이나 그림만으로 의미를 전달하지 않는다. 탭과 버튼의 터치 영역은 최소 44×44px로 하며, 하단 메뉴가 내용을 가리지 않게 안전 여백을 둔다. 모바일에서도 조회·직접 등록·수정·분류 변경·문서 열람·백업·복원을 모두 제공한다.

### 5.8 파스텔 색상과 귀여운 아이콘

| 요소 | 제안 값·스타일 |
| --- | --- |
| 전체 배경 | 따뜻한 아이보리 `#FAF8F5` |
| 카드 기본 | 화이트 `#FFFFFF`, 모서리 20~24px, 약한 그림자 |
| 보조 색 | 민트 `#DDF3E8`, 하늘 `#DDEFFA`, 라벤더 `#EAE3FA`, 연분홍 `#F9E1EA`, 버터 옐로 `#FFF1C7` |
| 본문 글자 | 짙은 회색 `#303846`, 보조 글자도 배경과 충분한 대비 확보 |
| 주요 버튼 | 차분한 짙은 초록 `#355E52`, 흰 글자 |
| 아이콘 | 둥근 윤곽, 작은 표정, 단순한 형태, 과도한 입체감·움직임 없이 통일 |
| 글자 | 한국어 시스템 글꼴, 본문 기본 16px, 제목·숫자는 계층 구분 |

색상은 구현 시 대비 검증 후 조정한다. 일반 글자는 4.5:1 이상을 목표로 하며 선택·오류·확인 필요는 텍스트와 테두리도 함께 표시한다. 아이콘은 직접 제작한 가벼운 인라인 SVG를 우선 사용하고, 외부 아이콘을 사용하면 이용 조건과 출처를 기록한다. 이미지에 글자를 구워 넣지 않으며 키보드 포커스·접근 가능한 버튼 이름을 제공한다. 아이콘을 단일 HTML 안에 넣어 오프라인에서도 표시되게 한다.

### 5.9 분류·화면 설정의 데이터 보존

보기 탭, 분류 이름, 보장과 분류의 연결, 분류 확인 상태, 정렬 순서 등은 원본 보험정보와 분리된 관리 메타데이터로 저장한다. 기존 백업에 이러한 정보가 없으면 읽기 시 기본값을 제공하고 원본 JSON을 재작성하지 않는다. 사용자가 확인한 분류와 설정은 관리 백업에 포함하고 복원 후 동일하게 표시되어야 한다.

대시보드 요약은 저장된 자료에서 계산한 조회용 결과다. 화면을 여는 것만으로 원본 가입금액·기간·ID·약관 연결을 변경하지 않는다. 신체 분류 사전의 수정이나 아이콘 교체로 기존 연결을 잃지 않도록 분류에도 안정적인 내부 ID를 사용하고 이름·아이콘을 별도 관리한다. 삭제한 분류에 연결된 보장은 확인 필요로 남기며 조용히 누락시키지 않는다.

### 5.10 대시보드 구현 요청 프롬프트

```text

PC 첫 화면은 요약 카드와 회사별·보장별·신체별 탐색이 있는 대시보드로,
모바일은 파스텔톤의 귀여운 아이콘과 한글 라벨이 있는 두 열 카드로 만들어줘.
같은 계약·보장 데이터를 세 보기에서 재사용하고 원본 ID·금액·문서 연결을 보존해줘.
분류는 수동 확인·다중 연결·미분류를 지원하고 관리 메타데이터에 별도 저장해줘.
건수의 집계 기준과 중복을 구분하고 금액은 증권상 가입금액으로 표시해줘.

예상 보험금 계산과 질병 위험도 분석은 구현하지 않아도 돼.
아이콘은 가벼운 SVG로 HTML 안에 넣고 PC·모바일 기능을 동일하게 제공해줘.
T01~T34 중 관련 테스트를 실행하고 완료·실패·미실행을 구분해 보고해줘.
```

## 6. 기존 자료의 활용과 확인 범위

참고한 기존 v5_1 개발계획서는 IndexedDB 저장, MD 증권·약관, 보험 보장 배열, 검색·변경 기록, 일반·전체 및 암호화 백업을 기술하고 있다. 이는 해당 계획서에서 확인한 구조이며, 이번 작업에서 사용자의 실제 브라우저 저장소나 모든 HTML 버전을 실행 검사한 결과는 아니다.

| 자료 | 이번 활용 | 보존 방법 |
| --- | --- | --- |
| 보험정보 | 목록·상세·편집 | 계약과 보장 ID, 원래 값·타입·미확인 상태 유지 |
| 증권·약관 MD | 텍스트 열람·수동 연결 | 원문, 페이지, 제목, 판·버전, 근거 위치 유지 |
| JSON 백업 | 기존 자료 가져오기 | 원본 파일 자체와 전체 데이터 구조 보관 |
| 질병코드 DB | 이번 필수 화면에서 사용하지 않음 | 기존 원본 프로젝트에서 보존, 후속 연결 대상 |
| 지급조건·과거 계산 결과 | 이번에는 계산하지 않음 | 모르는 필드까지 전체 보존 |
| 검색기록·변경기록·초안 | 필요 시 읽기용 보관 | 초기 가져오기에서 누락하거나 지우지 않음 |
| PDF·이미지 등 원본 | 백업에 실제 있으면 열람·보존 | 없는 원본을 복구했다고 표시하지 않음 |

실제 개발 착수 시 사용할 HTML과 백업 한 쌍을 기준본으로 지정하고, 파일명·파일 크기·해시·버전을 기록한다. 원본을 포함한 백업이 가능하면 이를 확보한다. 이미 원본이 제외된 백업에는 원본 파일을 새로 만들어 채우지 않는다.

## 7. 데이터 손상을 막는 핵심 설계

### 7.1 세 가지 공간을 분리한다

| 공간 | 목적 | 적용 원칙 |
| --- | --- | --- |
| 기존 GitHub 저장소 | 기존 코드·기획·기록 | 이번 작업에서 수정·이동·삭제하지 않음 |
| 새 GitHub 저장소 | 새 기획서와 이후 관리용 코드 | 개인 보험자료를 포함하지 않음 |
| 브라우저 관리 데이터 저장소 | 실제 개인 보험정보 | 기존 앱과 다른 DB 이름을 사용하고 기존 DB에 쓰지 않음 |

새 브라우저 DB 이름 제안은 `hidden-insurance-manager-v1`이다. 이는 앞으로 구현할 이름이며 현재 사용자의 브라우저에 생성됐다는 의미는 아니다. 기준 소스에서 기존 저장소 이름과 충돌하지 않는지 확인한 뒤 확정한다.

기존 계획서에 기록된 `hidden-insurance-note-v5-unlocked`, `hidden-insurance-extraction-v5-unlocked` 등 기존 저장소를 신규 앱이 갱신·삭제·초기화하지 않도록 쓰기 경로를 제한한다.

### 7.2 원본, 변경분, 화면용 데이터를 구분한다

```mermaid
flowchart TD
    A["기존 백업 사본"] --> B["원본 파일·전체 payload 보존"]
    B --> C["읽기 어댑터"]
    C --> D["내보험 관리 화면"]
    D --> E["사용자가 바꾼 값만 기록"]
    B --> F["관리 백업"]
    E --> F
    B -.-> G["후속 계산용 읽기 모델"]
    E -.-> G
```

- **원본 파일:** 가져온 파일의 바이트를 변경 없이 보관하고 해시를 기록한다. 원본 그대로 다시 내려받을 수 있어야 한다.
- **원본 데이터:** 지원되는 백업을 해석한 전체 payload를 보존한다. 화면에 필요한 몇 개 필드만 추려 원본을 대체하지 않는다.
- **변경 기록:** 사용자가 수정한 필드·이전 값·새 값·대상 ID·시간을 별도로 저장한다.
- **화면용 데이터:** 원본과 변경 기록을 읽어 화면에 맞게 구성한다. 정렬·필터·화면 재구성은 원본을 바꾸지 않는다.
- **백업:** 원본 보존분, 변경분, 새로 등록한 자료, 문서, ID 대응표를 함께 담는다.

이 구조는 보존 목표를 위한 제안이다. 실제 사용을 시작하기 전, 저장·복원 테스트로 구현이 이 원칙을 지키는지 확인해야 한다.

### 7.3 반드시 지킬 보존 규칙

| ID | 보존 규칙 |
| --- | --- |
| P01 | 기존 HTML·백업·GitHub 저장소·브라우저 DB를 덮어쓰지 않는다. |
| P02 | 가져온 원본 파일과 원본 payload는 수정하지 않는다. |
| P03 | 알 수 없는 필드와 중첩 객체도 보존한다. 알려진 필드만 복사하여 새 객체를 만들지 않는다. |
| P04 | 계약 ID·보장 ID·문서 ID를 유지한다. ID 충돌은 자료 묶음 ID로 구분하고 임의 병합하지 않는다. |
| P05 | 동일 보험사·동일 상품명이어도 계약 ID가 다르면 별도 계약으로 유지한다. |
| P06 | ID가 없는 항목은 별도 대응표를 만든다. 원본에 임의 ID를 덮어쓰지 않는다. |
| P07 | 빈 값·null·0·문자열 숫자를 구분한다. 화면 표시를 위한 변환으로 저장 타입을 바꾸지 않는다. |
| P08 | 지급조건·면책·감액·이력·근거를 관리 화면에서 쓰지 않더라도 삭제하지 않는다. |
| P09 | 문서 수정 시 이전 본문·버전·연결을 남긴다. 문서 삭제 대신 보관 처리를 우선한다. |
| P10 | 사용자 자료와 가상 체험 자료를 분리한다. 테스트 종료 시 사용자 자료를 초기화하지 않는다. |
| P11 | 오류가 나면 실패를 표시한다. 빈 데이터로 정상 저장하거나 새 자료로 덮어쓰지 않는다. |
| P12 | 기획서·HTML 업데이트만으로 실제 사용자 데이터를 자동 이관·초기화하지 않는다. |

### 7.4 불러오기·저장의 실패 처리

1. 파일을 임시 영역에서 읽고 형식, 지원 버전, 참조, 필드 수, 원본 포함 여부를 검사한다.
2. 계약·보장·문서 수와 누락 목록을 미리 보여준다. 불확실한 연결은 수동 확인 대상으로 둔다.
3. 새 자료 묶음으로 등록한다. 첫 구현에서는 서로 다른 백업의 자동 합치기를 제공하지 않는다.
4. 새 자료의 저장과 검증을 완료한 뒤 활성 자료를 전환한다. 여러 저장 작업은 하나의 트랜잭션 또는 검증된 임시본 전환으로 처리한다.
5. 용량 부족, 잘못된 암호, 손상된 JSON, 지원하지 않는 형식이면 활성 자료와 기존 DB를 유지한다.
6. 다른 탭에서 수정한 자료는 버전 충돌을 감지하고, 마지막 저장이 조용히 덮어쓰지 못하게 한다.

해시는 파일 변경을 확인하는 수단이며 필드의 의미나 연결의 정확성을 보장하지 않는다. 해시 비교와 함께 필드별 값·타입·참조 비교를 수행한다.

### 8.2 새 관리 백업의 개념 구조

아래 구조는 설계 예시다. 기존 앱의 실제 백업 형식과 같다고 주장하거나, 이를 실제 사용자 백업으로 제공하지 않는다.

```json
{
  "format": "hidden-insurance-manager-backup",
  "backupVersion": 1,
  "schemaVersion": 1,
  "appVersion": "0.1.0",
  "datasets": [],
  "activeDatasetId": null
}
```

각 자료 묶음에는 가져온 파일의 바이트와 해시, 원본 payload, 새 자료, 변경 기록, 문서, ID 대응표, 검증 요약을 담는다. 원본 바이트는 백업에 포함할 수 있는 안전한 직렬화 방식으로 보존한다. 원문을 두 번 담으면 용량이 증가하므로 실제 백업 크기를 측정하고, 보존 검증을 통과하는 범위에서 중복 저장을 줄인다.

새 관리 백업을 기존 HTML에서 바로 읽을 수 있다고 보장하지 않는다. 원래 백업은 원본 그대로 반환하고, 수정된 관리 자료는 새 관리 앱과 후속 통합 앱이 지원하도록 명시한다. 기존 앱용 변환 내보내기는 별도의 호환성 테스트를 통과한 뒤 추가한다.

### 8.3 계산 기능을 연결할 때의 원칙

- 계산기는 관리 화면과 같은 ID·읽기 모델을 사용한다.
- 계산 결과를 원래 가입금액이나 보장내용에 덮어쓰지 않는다.
- 계산 규칙·결과·사건일·사용한 데이터 버전·근거를 별도로 저장한다.
- 지급조건이 불명확하면 미확인 상태를 유지하고 금액을 임의 생성하지 않는다.
- 계산 추가 후에도 내보험 조회·수정·백업 기능이 동일하게 동작해야 한다.
- 계산 기능에 문제가 있으면 계산 부분만 비활성화하고 관리 데이터는 계속 읽을 수 있어야 한다.

## 9. 기획서 수정과 업데이트 정책

### 9.1 버전을 따로 관리한다

| 버전 | 예시 | 바뀌는 경우 |
| --- | --- | --- |
| 기획서 버전 | 기획 v1.0 → v1.1 | 범위·화면·요구사항 설명 변경 |
| 앱 버전 | 0.1.0 → 0.2.0 | HTML의 기능·화면·오류 수정 |

| 백업 형식 버전 | 1 → 2 | 내보내기·복원 형식 변경 |

기획서 버전이 바뀌었다고 데이터 스키마 버전을 자동으로 올리지 않는다. 화면 변경만으로 기존 데이터를 재작성하지 않는다. Git 커밋 이력은 코드·문서 복구에 사용하고 개인 보험정보 복구는 데이터 백업으로 처리한다.

### 9.2 변경 종류별 처리

| 변경 상황 | 필수 조치 | 데이터에 대한 기본 동작 |

| 기획서 문장 수정 | 문서 버전·변경 이유 기록 | 변경 없음 |
| 기획에 기능 추가 | 요구사항 ID·우선순위·영향 기록 | 구현 전까지 변경 없음 |
| 색상·레이아웃 수정 | 조회·입력·모바일 회귀 확인 | 변경 없음 |
| 새 선택 필드 추가 | 누락을 허용하고 미확인으로 읽기 | 기존 레코드에 임의 사실을 채우지 않음 |
| 필드 이름·의미 변경 | 호환 읽기 또는 명시적 변환 설계 | 원본 유지, 사본 변환 |
| 기능 보류·삭제 | 화면 노출과 데이터 보존을 구분 | 관련 데이터는 유지 |

| 이전 앱으로 되돌리기 | 지원 스키마 확인 | 미지원 자료에 쓰지 않음 |

### 9.3 업데이트 적용 순서

1. 변경 요청을 문서에 기록하고 영향을 받는 요구사항을 표시한다.
2. 현재 정상 버전의 코드와 기획서를 커밋하고, 사용자 자료는 별도 백업한다.
3. 사본 환경에서 변경을 구현한다. 테스트에는 가상 자료를 우선 사용한다.
4. 저장 구조가 바뀌면 구버전 입력을 읽는 어댑터와 변환 후 비교표를 만든다.
5. 변경 전후 필드·연결·원문·사용자 수정값을 비교하고 백업 왕복을 확인한다.
6. 통과한 변경만 안정 버전에 반영한다. 검증 실패 시 기존 안정 버전과 활성 데이터를 유지한다.
7. 실제 업데이트 후 오류가 나면 복구 절차에 따라 버전과 데이터를 맞춰 복원한다.

### 9.4 복구 기준

- **기획서 오류:** 이전 문서 커밋을 참고해 수정한다. 사용자 데이터는 건드리지 않는다.
- **화면·코드 오류:** 이전 안정 HTML을 사용한다. 해당 HTML이 새 데이터 형식을 지원하는지 먼저 확인한다.
- **데이터 변환 오류:** 변환 전 백업을 별도 자료 묶음으로 복원한다. 실패한 자료는 조사용으로 보존한다.
- **업데이트 후 추가 입력 존재:** 최신 자료를 먼저 백업한다. 예전 백업으로 덮어쓰면서 이후 입력을 잃지 않도록 차이를 확인하고 재적용한다.
- **구버전이 새 형식을 모르는 경우:** 읽기 전용 또는 열기 차단으로 처리하며, 빈 상태로 새로 저장하지 않는다.

코드만 되돌리면 모든 데이터까지 복구된다고 가정하지 않는다. 브라우저 저장소 삭제·기기 분실까지 대비하려면 사용자가 내려받은 외부 백업이 필요하다.

사용자가 안내한 미션 제출 조건에 따라 저장소를 공개한다. 공개 상태는 평가자가 결과물을 열람하기 위한 조건이며, 미션 통과 여부는 실제 구현·검증 기록과 공식 평가 기준을 함께 대조해야 한다.

### 10.2 파일 구성

| 경로 | 역할 | 생성 시점 |
| --- | --- | --- |
| `README.md` | 미션 연결·현재 범위·진행 상태·기획서 링크 | 이번 요청 |
| `미션2-2_1_내보험관리_개발기획서.md` | 이 문서 전체 | 이번 요청 |

### 10.3 개인자료 처리

실제 보험증권·약관 원본, 개인 보험정보 JSON, 암호화 백업, 계약번호·이름·주소가 들어 있는 캡처를 코드 저장소에 넣지 않는다. 공개 저장소에는 개발 코드·기획서·사용법·개인정보가 없는 검증 기록만 올린다. 평가용 데이터는 가상 자료를 사용하고, 실행 화면 캡처와 HTML 내장 데이터에도 실제 개인정보가 없는지 확인한다.

`.gitignore`는 실수 방지를 돕지만 이미 추적 중인 파일이나 강제 추가를 막지는 못한다. 매 커밋 전 변경 파일 목록과 개인자료 포함 여부를 확인한다. 필요한 코드 내 기본 DB는 개인정보가 없는지와 이용 조건을 확인한 후 별도로 추가한다.

기존 대용량 코드·라이브러리 제거는 의존관계를 조사한 후 새 사본에서만 수행한다. 파일 용량을 줄이기 위해 사용자 데이터나 필요한 근거를 제거하지 않는다.

HTML 파일을 새로 받는 것만으로 개인 자료가 자동 복사되지 않을 수 있다. 동일 브라우저라도 파일 위치·실행 방식에 따른 저장소 접근을 실제 확인한다. iPhone 파일 미리보기와 브라우저 실행은 별도로 검증하고, 지원한 실행 경로를 사용설명에 적는다.
